## Description
Pre-public audit finding, severity P1, from the review workflow over main at fcc6b66 on 2026-09-13. Raised by the packaging, tests lenses and confirmed by an adversarial verifier.

### From the packaging lens: No CI of any kind; nothing runs tests or lint on a pull request

Evidence: `ls .github` -> `cannot access '.github': No such file or directory`. No other CI config tracked (`git ls-files` shows none). The only enforcement is the pre-commit config, which is generated, gitignored (.gitignore line `.pre-commit-config.yaml`) and only exists inside the private-layer devenv shell, so an outside PR is checked by nothing.

Recommendation: Add `.github/workflows/ci.yml` running on push/PR with `astral-sh/setup-uv`, Python 3.12, `uv sync --all-groups`, `uv run pytest` (coverage gate is in addopts), `uv run ruff check .`, `uv run pylint src tests`, and a wheel-build + clean-venv install smoke step. Add `ruff` to `[dependency-groups] dev` so CI and contributors have it.

Verifier (P1, blocks public: no): Evidence reproduces exactly: `ls .github` fails, `git ls-files` contains no workflow/CI config of any provider (GitHub, GitLab, Circle, etc.), `.gitignore` line 4 ignores `.pre-commit-config.yaml`, and the only copy of that file is an untracked one generated by the cachix/git-hooks module pulled in via `devenv.yaml` and the private `inputs.devenv-layers` imports in `devenv.nix` (which also enables the ruff hook and points pylint at the venv). `pyproject.toml` `[dependency-groups] dev` has pytest/pytest-cov/pylint/black but no ruff, so a contributor without the private devenv layer cannot even run the same lint locally; the repo also has no git remote configured yet. So the finding is real and P1 is fair: the first outside PR gets no automated check and the author has no reproducible lint command. I do not agree it blocks going public, though: the code, tests, and 100%-coverage gate in addopts are all tracked and runnable with `uv sync --all-groups && uv run pytest`, nothing in README/docs promises CI, and a missing workflow file is additive polish that can land in the first commit after publication rather than a correctness or safety issue that must precede it. The recommended fix (a `.github/workflows/ci.yml` plus adding ruff to the dev group) is sound.

### From the tests lens: No CI, so the fidelity test against the real knot binary runs only on machines that happen to have knot

Evidence: No .github directory (`ls -a .github` -> no such file); no CI config of any kind in git ls-files. tests/reading/test_real_knot.py line 18-21 marks the module `slow` and `skipif(shutil.which("knot") is None, reason="knot is not on PATH")`. Running from a bare shell (`env -i ... .devenv/state/venv/bin/pytest -q`) gives `135 passed, 10 skipped`; the reason is only visible with `-rs` (`SKIPPED [9] tests/reading/test_real_knot.py:142: knot is not on PATH`). A contributor without knot never sees the recorded envelopes checked against the binary, and there is nothing that runs it on a PR.

Recommendation: Add a CI workflow that installs knot (or runs inside devenv once the input is public) and runs `pytest` plus `prek run --all-files`. Add `-ra` to addopts so the skip reason is printed in every run.

Verifier (P2, blocks public: no): The evidence reproduces exactly: `.github` does not exist, `git ls-files` has no CI/workflow config of any kind, tests/reading/test_real_knot.py lines 18-21 carry `pytest.mark.skipif(shutil.which("knot") is None, reason="knot is not on PATH")`, pyproject's addopts (`--cov=knotview --cov-report=term-missing --cov-fail-under=100`) has no `-ra`, and running pytest from `env -i PATH=/usr/bin:/bin` gives `135 passed, 10 skipped` with the reason only surfacing under `-rs` (`SKIPPED [9] tests/reading/test_real_knot.py:142` and `[1] :160`). knot itself comes only through the devenv shell (`/nix/store/...-knot-0.12.0/bin/knot`, via the devenv-layers input, which is a private `git+ssh://` URL in devenv.yaml). So the finding is real, but I disagree with P1/blocks_public: an 18-commit repository with no remote CI is ordinary for a first public push, a first outside user of the panel never touches this, and a contributor without knot gets a green run with the fake-backed unit tests still enforcing 100% coverage; the fidelity tests are an extra guard against fixture rot, not the primary correctness gate. The silent-skip half is a one-line `-ra` addopts fix and the CI half cannot even be done properly until the devenv-layers input is public (which the reviewer's own recommendation concedes), making that a separate, prior concern. This is polish that should be done soon after going public, not a gate on it.
